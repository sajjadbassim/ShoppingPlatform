# ميزات مطلوبة للإصدار القادم (تطبيقات الموبايل)

طلبها صاحب المشروع بتاريخ 2026-10-29 لتُنفَّذ في **الإصدار القادم**. تُسجَّل هنا فقط؛ لا تُنفَّذ قبل طلب صريح، ولا يُذكَّر بها.
لكل ميزة: ما طلبه المستخدم بلفظه تقريباً، ثم ملاحظات تقنية أولية للتخطيط (ليست قرارات).

---

## 1) تطبيق المندوب: مسح باركود الطلب بالكاميرا

**المطلوب**
- الباركود على الطلب **هو رقم الطلب نفسه** (مثل `ORD-20261029-0001`).
- مسح الباركود بكاميرا الهاتف **يعرض الطلب فقط** (يفتح شاشة تفاصيله).
- **التسليم يبقى يدوياً** كما هو الآن؛ الكاميرا للمسح وعرض الطلب فقط.

**ملاحظات تقنية**
- يحتاج حزمة `expo-camera` (ماسح باركود مدمج) وهي وحدة native، فتتطلب **بناءً جديداً** للتطبيق، ولا تعمل على نسخة المطور الحالية.
- لا يحتاج الباكند: الرقم يُبحث عنه في `useDriverOrders(false)` و`useDriverOrders(true)` (النشطة وسجل 7 أيام). إن لم يوجد: «هذا الطلب غير مُسند إليك».
- واجهة مقترحة: زر مسح في ترويسة تبويب الطلبات يفتح شاشة كاميرا، وعند القراءة يُغلق الماسح وينتقل إلى `/order/[id]`.
- صلاحية الكاميرا تُضاف إلى إعدادات التطبيق (`app.config.js`) وتُطلب عند أول استعمال.
- ملاحظة: كان قد أُضيف ثم أُلغي حقل «تأكيد برمز الطلب» داخل نافذة التسليم، لأنه لم يكن المقصود.

---

## 2) تطبيق الزبون، منتجات السوبر ماركت: «طبختي»

**المطلوب** (تظهر **في بداية** قسم السوبر ماركت)
- **تقترح وجبات:** «طبختي تقترح لي وجبات أسويها».
- **بالاسم:** أكتب اسم الطبخة فيعطيني **خيارات للمنتجات** التي يلزم أن أشتريها لها.

**ملاحظات تقنية أولية**
- مصدر الوصفات: (أ) جدول وصفات داخل الباكند (اسم، مكوّنات، كميات) يُربط كل مكوّن بتصنيف أو منتج، أو (ب) نموذج ذكاء اصطناعي يولّد قائمة المكوّنات من اسم الطبخة ثم يُطابَق كل مكوّن مع منتجات السوبر ماركت المتاحة بالبحث. (ب) أسرع انطلاقاً ويحتاج مفتاح API وتكلفة لكل طلب؛ (أ) أدق وأرخص تشغيلاً.
- نتيجة الطبخة: قائمة مكوّنات، لكل مكوّن منتج مقترح وبدائل، وزر «أضف الكل للسلة».
- «تقترح لي وجبات»: تقترح من الوصفات المتاحة حسب المنتجات المتوفرة في السوبر ماركت، ويمكن لاحقاً أن تراعي ما في السلة أو الطلبات السابقة.
- تحتاج هذه الميزة عمل **باكند** (نقاط API للوصفات/البحث) وتعديل الويب إن أُريد التوافق، وكلاهما يلزمه إذن صريح قبل التنفيذ.

---

## 3) تطبيق الزبون، الصفحة الرئيسية: «لبّسني»

**المطلوب**
- خيار «لبّسني» في الصفحة الرئيسية للزبون.
- يدخل الزبون **الطول والوزن (العرض)**، و**الألوان** التي يريد ارتداءها.
- يعطيه النظام **موديلات ملابس بالألوان** المختارة.
- **المناسبات:** رسمي، كاجوال، بدلة عرس، وغيرها.
- **صورة شخصية:** يأخذ الزبون صورة لنفسه أو **لوجهه فقط**، ويعطيه النظام **صورة خاصة به** وهو يرتدي الملابس المقترحة.

**ملاحظات تقنية أولية**
- الاقتراحات: مطابقة المناسبة واللون والمقاس (من الطول والوزن) مع منتجات الملابس في المتجر، فتكون الموديلات المقترحة منتجات يمكن شراؤها فعلاً.
- الصورة بالملابس (تجربة افتراضية Virtual try-on): تحتاج خدمة توليد/تركيب صور بالذكاء الاصطناعي، وتكلفة لكل صورة وزمن انتظار، وصور منتجات واضحة.
- **الخصوصية:** صور الوجه بيانات حساسة. يلزم موافقة صريحة قبل الرفع، وعدم الاحتفاظ بالصورة أكثر من اللازم، وإمكان حذفها، وبيان الجهة التي تُرسَل إليها. تُحدَّد هذه السياسة قبل البناء.
- الكاميرا والمعرض: `expo-camera`/`expo-image-picker` (وحدات native؛ ضمن البناء الجديد).
- تحتاج هذه الميزة عمل **باكند** (ملف المقاسات والتفضيلات، وربط خدمة الصور) يلزمه إذن صريح قبل التنفيذ.

---

## 4) لوحة الزبون: «embedded system»

**المطلوب كما ذُكر:** «ميزة embedded system للوحة الزبون».

**غير واضح، يُحسم قبل التخطيط** (لم يُسأل عنها الآن بطلب المستخدم ألا يُذكَّر بها):
- هل المقصود **تضمين** (Embed) لوحة الزبون أو متجر وسيط داخل موقع أو تطبيق طرف ثالث (iframe أو أداة مضمّنة)؟
- أم نظام مدمج داخل لوحة الزبون نفسها (وحدات ومزايا مدمجة)؟
- أم شيء آخر؟

---

## ملخص التبعيات للبناء القادم

| الميزة | يحتاج بناءً جديداً (وحدة native) | يحتاج باكند | إذن صريح مطلوب |
|---|---|---|---|
| مسح باركود (المندوب) | نعم: `expo-camera` | لا | لا (تطبيق فقط) |
| طبختي (الزبون) | لا | نعم | نعم |
| لبّسني (الزبون) | نعم: كاميرا/صور | نعم + خدمة صور | نعم |
| embedded system | يُحدَّد | يُحدَّد | نعم |

يُضاف إلى البناء القادم أيضاً: ملف Firebase للمندوب (`google-services.json` جاهز في مجلد التطبيق) لتعمل إشعارات الدفع.
